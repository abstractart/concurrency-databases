# Пессимистичные и оптимистичные транзакции: PostgreSQL vs MySQL

Набор самодостаточных демо-кейсов на одной таблице `accounts`:

```
accounts(id, owner, balance, version, updated_at)
```

- **Python-кейсы** (`cases/*.py`) сами создают конкуренцию: две-три транзакции
  стартуют синхронно через barrier, каждый шаг пишется в лог с таймстемпами,
  в конце печатается фактическое и ожидаемое состояние. Перед каждым запуском
  таблица пересоздается в чистое состояние.
- **SQL-кейсы** (`sql/pg/*.sql`, `sql/mysql/*.sql`) — те же сценарии для ручного
  прогона в двух (трёх) окнах `psql` / `mysql`: блок «Терминал 1», блок
  «Терминал 2» и ожидаемый результат в комментариях.

## Быстрый старт

```bash
docker compose up -d                      # PostgreSQL 16 (:5432) и MySQL 8 (:3306)
docker compose ps                         # дождаться healthy
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

python run_all.py                         # сразу все 14 кейсов на обеих СУБД (28 прогонов)

python3 cases/p0_lost_update.py --db pg   # или отдельный кейс
python3 cases/p0_lost_update.py --db mysql
```

У `run_all.py` есть фильтры: `--dbs pg`, `--filter deadlock` (подстрока имени),
`--verbose` (показывать вывод кейсов вживую), `--timeout N` (сек на кейс).
Сводная таблица в конце; код возврата 1, если хоть один прогон упал.

Каждый скрипт принимает `--db pg` или `--db mysql` и выводит
`ОЖИДАЕМЫЙ РЕЗУЛЬТАТ` в конце — сверьте с логом.

Параметры подключения переопределяются переменными окружения:
`PGHOST/PGPORT/PGUSER/PGPASSWORD/PGDATABASE`, `MYSQLHOST/MYSQLPORT/MYSQLUSER/MYSQLPASSWORD/MYSQLDATABASE`.

## Две стратегии в двух словах

| | Пессимистичная | Оптимистичная |
|---|---|---|
| Идея | «Заблокирую строку, пока с ней работаю» | «Не блокирую; при записи проверяю, что никто не изменил её до меня» |
| Механика | `SELECT ... FOR UPDATE / FOR SHARE`, advisory-блокировки, таймауты, `SKIP LOCKED` | версионный столбец / `updated_at` в `WHERE`, `SERIALIZABLE` + retry |
| При конфликте | вторая транзакция **ждёт** (или падает по таймауту/`NOWAIT`) | первая проходит, вторая **повторяется** |
| Когда выбирать | горячие строки, короткие транзакции, очереди задач, конфликты почти гарантированы | конфликты редки, транзакции длинные (внешние вызовы), много читателей |

## Кейсы

### Пессимистичная стратегия

| Файл | Что демонстрирует |
|---|---|
| `p0_lost_update` | **Мотивация**: read-modify-write без блокировок теряет обновление молча |
| `p1_for_update` | `SELECT ... FOR UPDATE`: второй писатель ждёт и читает уже актуальное значение |
| `p2_share_lock` | `FOR SHARE`: читатели параллельны, писатель ждёт всех читателей |
| `p3_skip_locked_nowait` | `SKIP LOCKED` / `NOWAIT`: очередь задач без ожиданий и драк за строку |
| `p4_deadlock` | Встречные переводы → deadlock (PG `40P01`, MySQL `1213`); фикс — порядок блокировок по id |
| `p5_lock_timeout` | `lock_timeout` (PG `55P03`) / `innodb_lock_wait_timeout` (MySQL `1205`): не ждать вечно |
| `p6_advisory` | `pg_advisory_lock` / `GET_LOCK`: мьютекс приложения вне строк таблицы |
| `p7_crm_long_transaction` | **Анти-паттерн CRM**: транзакция открыта, пока пользователь «редактирует» → таймауты сохранений у конкурентов и исчерпание пула соединений |

### REPEATABLE READ

| Файл | Что демонстрирует |
|---|---|
| `r1_rr_snapshot` | Снапшот: оба чтения внутри RR-транзакции видят старое значение (одинаково в PG и MySQL) |
| `r2_rr_write_conflict` | **Главное различие**: при записи PG → `40001` (lost update невозможен), MySQL → обновление молча теряется |
| `r3_rr_relative_update` | RR + «`SET balance = balance − X`» (считает СУБД): MySQL применяет к актуальной строке (потери нет), PG → всё равно `40001` |

### Оптимистичная стратегия

| Файл | Что демонстрирует |
|---|---|
| `o1_version_retry` | `UPDATE ... WHERE id = ? AND version = ?`: конфликт = 0 строк → retry |
| `o2_updated_at` | Та же оптимистика через метку времени, без изменения схемы |
| `o3_serializable_retry` | `SERIALIZABLE` + retry: PG (SSI, `40001`) vs MySQL (блокировки, конфликт как `1213`/`1205`) |

Ручные SQL-версии: `sql/pg/<имя>.sql` и `sql/mysql/<имя>.sql`
(у P7 SQL-версии нет: анти-паттерн живёт на уровне приложения — незакрытые
транзакции и соединения между HTTP-запросами).

## Ключевые различия PostgreSQL и MySQL (InnoDB)

| Аспект | PostgreSQL | MySQL 8 (InnoDB) |
|---|---|---|
| Дефолтный isolation | READ COMMITTED | REPEATABLE READ |
| RR защищает от lost update? | **Да**: ошибка `40001` на UPDATE/COMMIT | **Нет** при `SET balance = <из приложения>`; **да** при вычислении в запросе (`SET balance = balance − X` — current read), но без ошибки — см. R2/R3 |
| `SERIALIZABLE` | SSI: «чистая» оптимистика, конфликт = `40001` | Реализован блокировками (`SELECT` → shared lock); конфликт = `1213` / `1205` |
| Коды для ретрая | `40001`, `40P01` | `1213`, `1205` (см. `RETRYABLE` в `demo/db.py`) |
| Advisory-блокировки | `pg_advisory_lock(key)` | `GET_LOCK('имя', timeout)` |
| `SKIP LOCKED` / `NOWAIT` | есть | есть (8.0+) |
| Таймаут ожидания блокировки | `lock_timeout` → `55P03` | `innodb_lock_wait_timeout` → `1205` (по умолчанию откатывает только запрос) |
| Разделяемая блокировка | `FOR SHARE` | `FOR SHARE` (8.0), ранее `LOCK IN SHARE MODE` |

## Подтверждённые результаты прогонов

Зафиксировано 2026-11-01 на окружении из `docker-compose.yml`
(PostgreSQL 16, MySQL 8.0) командой `python run_all.py` — **28/28 прогонов
успешно**. Поведение (ошибки, коды, итоговые балансы) стабильно от запуска
к запуску; тайминги зависят от машины.

| Кейс | PostgreSQL 16 | MySQL 8.0 |
|---|---|---|
| `p0_lost_update` | итог **800 вместо 700** — обновление потеряно молча, без ошибок | то же |
| `p1_for_update` | T2 ждал на `FOR UPDATE` 1.31 с, прочитал актуальные 900 → итог **700** | ждал 1.32 с → итог **700** |
| `p2_share_lock` | оба читателя получили `FOR SHARE` за 0.00 с; писатель ждал 1.80 с → итог **1500** | то же |
| `p3_skip_locked_nowait` | W2 взял id=2, не ожидая занятый id=1; `NOWAIT` → ошибка **`55P03`** мгновенно | `NOWAIT` → **`3572`** мгновенно; итог id=1, id=2 → 1100 |
| `p4_deadlock` | сценарий A: **`40P01`** (детект ~1 с), применён один перевод; сценарий B: оба прошли | A: **`1213`** (детект мгновенный); B: оба прошли; сумма 2000 сохраняется |
| `p5_lock_timeout` | T2 прервался через 1.01 с с **`55P03`** (строка держалась 3 с) | через 1.00 с с **`1205`** |
| `p6_advisory` | T2 вошёл в «критическую секцию» через 1.51 с; try-lock: ключ 42 занят, 43 свободен | то же через `GET_LOCK` |
| `p7_crm_long_transaction` | M1 держал строку 6 с: M2 не сохранил вовсе — **`55P03`** после 2.0 с; M3 — со 2-й попытки; 4-й пользователь: «пул исчерпан» | M2/M3 — **`1205`** после 2.0–2.5 с; M3 — с 3-й попытки; пул исчерпан так же |
| `r1_rr_snapshot` | оба чтения в RR-транзакции видят 1000, после COMMIT — 700 | одинаково |
| `r2_rr_write_conflict` | T2 → **`40001`** на UPDATE, итог **900** (потери нет, нужен ретрай) | конфликт не обнаружен: обе «успешны», итог **800** (потеря) |
| `r3_rr_relative_update` | T2 → всё равно **`40001`**, итог **900** | `UPDATE` делает current read: 1000 → 900 → **700** без ошибок |
| `o1_version_retry` | ровно один конфликт («0 строк обновлено») → ретрай → **700**, version = 2 | идентично |
| `o2_updated_at` | конфликт по метке → ретрай → **700** | идентично |
| `o3_serializable_retry` | **`40001`** (SSI) → ретрай → **700** | конфликт как deadlock **`1213`** → ретрай → **700** |

Таймлайны самых показательных кейсов:

```text
R2 — app-computed запись в RR (SET balance = <посчитано в приложении>):
  pg    | T1 | записал balance = 900.00, commit прошёл без ошибок
  pg    | T2 | ❌ SerializationFailure, код 40001: could not serialize access …
  mysql | T1 | записал balance = 900.00, commit прошёл без ошибок
  mysql | T2 | записал balance = 800.00, commit прошёл без ошибок   ← потеря!

R3 — вычисление в запросе (SET balance = balance − X):
  pg    | T1 | UPDATE прошёл, commit ✅; после commit: balance = 900.00
  pg    | T2 | ❌ SerializationFailure, код 40001 …                  ← итог 900
  mysql | T1 | UPDATE прошёл, commit ✅; после commit: balance = 900.00
  mysql | T2 | UPDATE прошёл, commit ✅; после commit: balance = 700.00 ← current read
```

## Когда что выбирать

**Пессимистично** (`FOR UPDATE`, `SKIP LOCKED`):
- спор за одни и те же горячие строки почти гарантирован, и retry дороже ожидания;
- очереди задач (`SKIP LOCKED`) и «критические секции» (advisory-блокировки);
- транзакции короткие — блокировки не будут копиться.

**Оптимистично** (version + retry, `SERIALIZABLE` + retry):
- конфликты редки (редактирование профиля, настроек, документов);
- транзакции длинные или включают внешние вызовы — держать блокировки нельзя;
- много читателей, мало писателей; распределённые приложения без общей памяти.

Практическое правило: если инкремент самодостаточен (`SET balance = balance - x`),
атомарный `UPDATE` часто закрывает вопрос без обеих стратегий.
